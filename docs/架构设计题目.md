### **模块一：Context / Performance**

2.一个 session 连续聊了 200 轮，context 快爆了。你会怎么做压缩？如何确保压缩后的对话仍然流畅？

答：压缩时做token输出的预留，也就是当前上下文窗口的长度再加上要保存的最近n轮会话，再加上预留的输出tokens，如果大于设定的上下文阈值，则进行压缩，并且系统明确压缩范围，system prompt和工具信息不压缩，在压缩时，将压缩的内容生成为一份结构化的摘要，例如可以保留目的，决策，进度，未实现的内容，用户偏好。然后追加到上下文中，接着再把保留的最近n轮会话追加会messages里。
如果压缩后的内容还是超过上下文，那么久继续压缩，设置一个重复压缩上限，超过阈值直接报错停止压缩。

### **模块二：Memory**

1.和聊天 Agent 熟悉半个月后，用户问了一个以前问过的问题。Agent 如何做 memory 召回更合理？

答：应该做关键词匹配和向量检索，关键词用于匹配具体的术语信息，向量检索用于找到表达含义类似的历史问题。然后结合当前问题判断召回的信息是否有用，这个判断的角度可以用相关性、可靠性、有效性以及意图是否一致来考量。如果召回的内容与当前上下文和短期记忆冲突，应当由用户进行确认。
如果当前上下文较记忆新增了新的内容，应当已当前上下文为准。
如果没有命中或者召回有用的信息，那么就基于当前信息回答，缺失时明确不回答。

### **模块三：Task** 

1.对于长程任务，大模型执行一段时间可能会忘掉目标，你知道哪些解决方案，有什么优缺？

答：
1. 任务拆分：在任务执行前明确最终目标以及约束和验收标准，然后将任务进行拆分，例如可以进行阶段性拆分，拆分成阶段性的子任务和阶段性目标，保存为一份markdown，每当完成一次阶段性的内容或者子任务时都对markdown文档进行更新，更新进度和已实现的内容和采用的方案。

优点：降低总任务复杂度，可观测性强，可以查找定位哪个环节出现问题，上下文可控

缺点：如果规划不明确或者标准以及目标不清晰，可能会导致实现时偏离任务。模型有幻觉，可能没来得及更新文档或者更新错误，导致后续任务接连出错。

2. 在上下文压缩时明确压缩的范围和结构，把任务压缩成结构化的摘要，保留对应的目标、决策、进度。
   优点：减少噪声、保留任务细节
   缺点：摘要可能遗漏约束或者其他细节
3. 采用编排模式开发，由规划层agent根据任务复杂度拆分任务，派发对应的subagent进行任务实现，并总结返回的产物和结论，根据返回的内容动态调整结果和计划。
   优点：上下文可控，减少无关信息干扰。
   缺点：任务交接可能会有遗漏，导致细节丢失。并且难以排查错误。仅适合任务上下文相关性不高的任务。

### **模块四：Tool / Session Runtime**

1.Agent 工具有同步和异步两类。异步工具不能让用户一直等，但结果依然重要。你会如何设计异步工具执行和完成通知？

答：首先调用异步工具时，保留和记录对应的工具调用id和任务id以及会话id，并在前端告知用户任务正在进行。此时工具调用会在后台进行，并通过类似SSE这种传输方式推送给前端，让用户能看到工具调用的实时记录。
工具调用结果返回后，agent通过对应的工具调用id和任务id匹配对应的工具调用消息，拿到对应的结果，并把工具调用状态设置为成功，然后推送前端，接着继续思考或者工具调用。

### **模块五：Agent Runtime 架构对比**

1.Claude Code 的工具输出方式和国内 GLM / 豆包等 OpenAI-compatible function calling 有什么不同？他们各自这样设计的优缺点是什么？

答：Claude Code的工具调用是一个content中的tool_use块，工具输出是一个role为“user” 且 带tool_result类型和tool_use_id作为标识的content块，结束标志是stop_reason: tool_ues，而OpenAI-compatible function calling是一个tool_calls数组，输出是role为"tool"，带tool_call_id的json字段，结束标志是finish_reason: tool_calls。

Claude Code这种设计便于所有文本和工具调用以及其他内容类型统一使用一种风格，也就是全局只有assistant类型和user类型。缺点是需要处理不同content块类型。

而openai-compatible function caliing职责分明，便于定位和观测。缺点是兼容端点不一定都统一，可能需要做对应的适配。
