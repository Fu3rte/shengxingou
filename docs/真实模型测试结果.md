## 压缩的关键证据

### 真实 usage 驱动场景

准备四段合成归档历史，每段用户文本约 11,000 字符，均低于 API 单条输入限制。随后实际调用模型，请其仅回复“收到”。

这次调用：

- 完整输入字符估算：**12,033.5 token**。
- 模型实际回报：输入 **25,301**、输出 **3**、总计 **25,304 token**。

再次询问项目和校验口令时：

- 完整请求字符估算：**12,054.25 token**。
- usage 基准加新增消息估算：**25,315.5 token**。
- 加输出预留：**29,315.5 > 20,000**，触发压缩。
- 字符估算加输出预留为 **16,054.25**。

三次都出现 `compact.request`、`compact.completed`，摘要保留“松岚”“K9R4”，最终回答正确。

压缩后真实业务输入分别为 **13,474、13,462、13,525 token**。JSON 请求字符量缩减分别为 **45.90%、45.96%、45.73%**。两种计量分别记录，字符缩减率不当作实际 token 缩减率。

再次关闭 Agent、按原 session ID 恢复后，三次均能回答两条事实。后续计量基准处于约 13.5k—13.7k，没有反复沿用压缩前的 25k 基准。

合成归档阶段没有模型 usage；第一次真实调用出现的超预算已经保留在“实际预算观察”指标中。

### 冷启动估算场景

初始完整请求为 **77,599 字符，估算 19,399.75 token**，加 4k 预留超过预算，生成摘要。

压缩后完整请求分别为 **20,757、20,682、20,721 字符**；真实业务输入分别为 **11,845、11,803、11,823 token**。三次摘要及最终答案均保留目标事实。

### 无可压缩前缀的边界

本场景保留完整消息组后可压缩前缀为空，三个案例均没有生成摘要，事实回答正确。单条旧用户消息约 55,000 字符，属于 runtime 合成历史，超过 HTTP API 的单条用户输入限制。

当前设计允许这一分支在原有字符输入限制内继续执行。结果不表示这类输入满足实际 20k token 硬限制。
